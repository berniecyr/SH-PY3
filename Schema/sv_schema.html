How the stores relate

Every camera location string (camLoc) is the join key across objdb2, clipdb and camdb — there is no numeric camera id anywhere in the schema. Dashed lines above are relationships the application code resolves at query time; solid lines are the two places a value is copied wholesale from one store into another.

No declared foreign keys anywhere

None of the four databases above uses an SQL FOREIGN KEY constraint. Every cross-table link — motion.objUid → objects.uid, clips.camLoc ↔ objects.camLoc, clipsToSend.objList → objects.uid — is convention enforced only by application code. It's workable because nothing here ever deletes a referenced row out from under a dependent one; it does mean a hand-edited row can silently orphan its children.

rules\*.rule · rules\*.query

pickle rules\<name>.rule + rules\<name>.query

Every saved rule is two pickle files that share a filename stem, and the split is the single most surprising thing in this schema: the schedule lives only in the .rule, while everything the Search window matches on lives in the .query. The stem is the rule name — there is no id — so renaming a rule renames both files. 94 rules on this install.

<name>.rule

when the rule may fire, and on which camera a pickled RealTimeRule
attributetypemeaning
_queryNamestrstem of the paired .query — the join between the two halves
_cameraLocationstrFK camera location — same camLoc key used across objdb2, clipdb and camdb
_isEnabledboolwhether the live rule engine runs this rule
_scheduledictdayType / customDays, is24Hours, start+stop Hour/Min, start+stop Type (fixed / sunrise / sunset), start+stop Offset, latitude, longitude
The schedule is here and nowhere else. It is not on the query model, so any code path that loads a rule by name and gets None silently falls back to a default 24/7 schedule — the cause of two separate bugs (duplicate-rule losing its schedule; retrospective Search ignoring it).

<name>.query

what the rule matches, and what it does about it a pickled SavedQueryDataModel
attributetypemeaning
_name / _visibleNamestrrule name; normally both equal the filename stem
_videoSourceobjVideoSourceBlockDataModel — holds _locationName
_targetslistwhat to look for (person / animal / vehicle / object, faces, nudity)
_triggerslistregion / line / door / duration / min-size blocks. A duration block's _moreThanValue is the usual reason two "identical" rules return different result counts — compare these before anything else.
_responseslistpairs of (kind, config-dict) — RecordResponse, SoundResponse, email, FTP, push, webhook, iHost, snapshot, local export
_lastEditedtupleDEP UI bookkeeping — which editor block was touched last
SoundResponse.soundPath is an absolute path into whichever source tree was running when the rule was saved, so rules survive a tree move with dead paths. Harmless while the response is disabled — it only trips NetworkMessageServer's path validation — but 58 of the 64 sound paths on this install point at trees that no longer exist.

live\

binary rings live\<camLoc>.audio · .live · .snaps\

Per-camera runtime buffers, not persistent data — written continuously by the camera process and read by the front end. Three per camera (48 entries for this fleet). Safe to delete while the app is stopped; they are recreated on the next camera start.

live\<camLoc>.*

three runtime buffers per camera entries 48
entryformmeaning
<camLoc>.audioPCM rings16le live audio, teed off the recorder's ffmpeg so live listening costs the camera no extra RTSP session. Read via AudioRingReader.
<camLoc>.livemmaplatest live-view frame. Since single-stream it is resized from the 640-wide analysis frame, not the raw substream — which is why the enlarged live view is softer than it used to be on cameras with a good substream.
<camLoc>.snaps\JPEG dirrolling full-resolution stills (~40 s retention) feeding the face/nudity full-res path. Under single-stream written at a fixed 1 fps; on the two-session path, one per keyframe. A file's mtime must equal its content's capture moment — mixing a fixed rate with keyframe-only decoding forges fresh timestamps onto stale pixels, which is exactly how the full-res face path broke once.
